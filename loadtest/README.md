# Нагрузочное тестирование

Сценарии для [k6](https://grafana.com/docs/k6/latest/) — инструмента нагрузочного тестирования
от Grafana Labs. Сценарии — это обычный JavaScript, k6 сам считает задержки, ошибки и трафик
и рисует графики. Генератор нагрузки — свой ноутбук, цель — прод.

| Сценарий | Что меряет |
|---|---|
| `smoke.js` | всё отвечает, кэш работает, `/api/` закрыт. Запускать перед любым тестом |
| `limits.js` | защита: с обычного адреса лимиты nginx отвечают 429 |
| `pages.js` | сколько страниц в секунду выдержит сайт: из кэша и мимо него (`BUST=1`) |
| `visitor.js` | посетитель целиком: страница плюс ~100 картинок и скрипты, как в браузере |
| `bandwidth.js` | канал сервера: параллельное скачивание большого файла |

## Установка

Ничего ставить не нужно, достаточно Docker: `loadtest/k6.sh` запускает k6 из официального
образа `grafana/k6`. Пока тест идёт, графики видны на <http://localhost:5665>. После теста в
`loadtest/results/` остаются отчёт с графиками (`.html`, годится для диплома) и итоговая
таблица (`.txt`).

```bash
loadtest/k6.sh smoke.js
loadtest/k6.sh pages.js -e RATES=50,100,200
```

Если хочется поставить k6 в систему (Ubuntu/Debian, [официальная инструкция](https://grafana.com/docs/k6/latest/set-up/install-k6/)):

```bash
sudo gpg --no-default-keyring --keyring /usr/share/keyrings/k6-archive-keyring.gpg \
  --keyserver hkp://keyserver.ubuntu.com:80 --recv-keys C5AD17C747E3415A3642D57D77C6C491D6AC1D69
echo "deb [signed-by=/usr/share/keyrings/k6-archive-keyring.gpg] https://dl.k6.io/deb stable main" \
  | sudo tee /etc/apt/sources.list.d/k6.list
sudo apt-get update && sudo apt-get install k6
# дальше: k6 run loadtest/smoke.js; графики: K6_WEB_DASHBOARD=true k6 run ...
```

## Настройки сценариев

Задаются как `-e ИМЯ=значение`:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `BASE_URL` | `https://zmsh.space` | куда стрелять |
| `INSECURE` | — | `1` — не проверять сертификат (локальный stage) |
| `RATES` | своё у сценария | ступени нагрузки через запятую: запросов (или посетителей) в секунду |
| `STEP` | `2m` | сколько держать каждую ступень (плюс 30 с разгона) |
| `MAX_VUS` | `200` | потолок одновременных «пользователей» k6 |
| `PATHS` | `/` | страницы через запятую, например `/,/<slug статьи>` |
| `BUST` | — | `pages.js`: `1` — каждый запрос мимо кэша nginx |
| `FILE` | — | `bandwidth.js`, `limits.js`: путь к большому файлу, например `/uploads/…jpg` |

Нагрузка задаётся частотой, а не числом пользователей: k6 запускает новые запросы с нужной
скоростью, даже если сервер начал тормозить. Так ведут себя настоящие посетители, и так
видно, где сервер перестаёт успевать.

## Ноутбук как генератор: что учесть

Ноутбука хватит с запасом: k6 на обычном ноутбуке выдаёт тысячи запросов в секунду. Ограничения:

1. **Отключите VPN до сайта.** У клиентов WireGuard в `AllowedIPs` прописан адрес сайта
   (`80.87.109.102/32`), поэтому с включённым VPN весь тест пойдёт через шлюз «Садалбари»
   (1 vCPU) и померяет его. Да ещё с адреса админов. Netdata при этом открывается только
   через VPN. Выход — вторая копия конфига WireGuard, в которой из `AllowedIPs` убран
   `80.87.109.102/32`: Netdata и SSH пойдут через VPN, а сайт напрямую.
2. **Кабель вместо Wi-Fi** и speedtest перед тестом. Тесты из кэша и `bandwidth.js` упрутся
   в домашний интернет раньше, чем в сервер. Если `data_received` ≈ скорости из speedtest,
   вы померяли свой канал, а не сайт.
3. **Один IP.** Лимиты nginx (10 страниц/с, 4 скачивания оригиналов) и fail2ban (100 запросов
   в минуту → бан на час) остановят тест почти сразу. Для замеров ёмкости свой адрес нужно
   временно добавить в исключения (ниже). Проверку самой защиты делайте до этого.
4. **Домашний IP может смениться** (особенно у мобильного интернета): проверяйте его перед
   каждой сессией.
5. **NetAngels** может принять тест за атаку. Перед большими тестами (`visitor.js`,
   `bandwidth.js`) стоит написать в поддержку, когда и с какого адреса будет нагрузка.

## Порядок на проде

### 0. Подготовка (один раз)

На ВМ сайта, через VPN:

```bash
cd /opt/wms-site && git pull && npm run prod   # nginx с кэшем и лимитами
sudo infra/vm/setup.sh firewall                # лимит соединений на IP + порт Netdata для LAN
npm run monitoring:up                          # Netdata
```

Netdata: `http://192.168.0.1:19999` (через VPN). Если интерфейс предложит войти в Netdata
Cloud, это не нужно: агент работает и без аккаунта. Смотреть:

- **Containers & VMs → wms_front, wms_strapi, wms_strapi_db, wms_nginx**: CPU и память
  каждого контейнера. 100% у одного ядра — это потолок Node;
- **System → CPU, RAM, swap**: вся ВМ. Если пошёл swap, памяти мало;
- **Network → eth0 (публичный интерфейс)**: исходящий трафик, тут виден потолок канала;
- **nginx → connections, requests**: сколько соединений держит nginx.

### 1. Смоук и проверка защиты (с обычного адреса, без исключений)

```bash
loadtest/k6.sh smoke.js
loadtest/k6.sh limits.js -e FILE=/uploads/Alina_Zyryanova_e345cbe4aa.jpg
```

`limits.js` делает около 65 запросов: это ниже порога fail2ban, но запускайте его не чаще раза
в минуту. Если всё-таки забанило:
`docker exec wms_fail2ban fail2ban-client set nginx-flood unbanip <ваш IP>`.

### 2. Снять лимиты со своего адреса

```bash
# Свой адрес — таким, каким его видит сайт. Сервисы вроде ifconfig.me не годятся,
# если трафик к ним идёт другим маршрутом (например, через другой VPN). Надёжно —
# прогнать smoke.js и посмотреть адрес в логе на ВМ сайта:
grep zmsh-loadtest nginx/logs/access.log | tail -1 | cut -d' ' -f1

# на ВМ сайта:
echo "<ваш IP> 1;" >> nginx/limit-exempt.conf && docker exec wms_nginx nginx -s reload
docker exec wms_fail2ban fail2ban-client set nginx-flood addignoreip <ваш IP>
```

Лимит в 256 TCP-соединений с IP (файрвол) остаётся, поэтому `MAX_VUS` не поднимайте выше 200.

### 3. Тесты

Каждый тест — 10–15 минут. Между тестами дайте серверу минуту отдохнуть. Во время теста
держите открытым Netdata.

```bash
# а) Мимо кэша: потолок Next + Strapi + Postgres. Это и есть «как было до кэша»
loadtest/k6.sh pages.js -e BUST=1 -e RATES=2,5,10,20,40

# б) Из кэша: так сайт видят посетители. Скорее всего упрётся в домашний канал
loadtest/k6.sh pages.js -e RATES=50,100,200,400

# в) Посетитель целиком. Начните с малого: первые посетители прогревают кэш картинок
loadtest/k6.sh visitor.js -e RATES=1,2,5,10,20

# г) Канал сервера (минимум из него и вашего интернета)
loadtest/k6.sh bandwidth.js -e FILE=/uploads/Alina_Zyryanova_e345cbe4aa.jpg -e VUS=8 -e DURATION=1m

# д) Долгий тест на утечки памяти: половина «колена» из (а), 30 минут.
#    В Netdata память wms_front и wms_strapi должна выйти на плато, а не расти
loadtest/k6.sh pages.js -e BUST=1 -e RATES=<половина колена> -e STEP=30m
```

Статья для `PATHS` — любой slug из админки (Content Manager → Article).

### 4. Вернуть как было

```bash
git checkout nginx/limit-exempt.conf && docker exec wms_nginx nginx -s reload
docker exec wms_fail2ban fail2ban-client set nginx-flood delignoreip <ваш IP>
```

Netdata можно не выключать: он занимает ~250 МБ памяти и копит историю.

## Как читать результаты

В итоговой таблице k6 и отчёте:

- `http_req_duration` — время ответа; смотрите `p(95)` и `p(99)`, а не среднее;
- `http_req_failed` — доля ошибок; разбивка — в `checks`: 503 — сработал `max_conns`
  (Next занят), 429 — лимит IP (адрес не в исключениях);
- `http_reqs` — сколько запросов в секунду реально получилось;
- `data_received` — трафик; сравните со speedtest;
- `page_full_load` (`visitor.js`) — сколько грузится страница со всеми ресурсами.

**«Колено»** — ступень, на которой `p(95)` резко растёт или появляются ошибки. Нагрузка
чуть ниже колена — это и есть ёмкость сайта.

Что видно в логе nginx на ВМ (`nginx/logs/access.log`, поле `rt=` — время ответа,
`cache=` — HIT/MISS/STALE):

```bash
# разбивка по статусу и кэшу за тест (UA теста помечен zmsh-loadtest)
grep zmsh-loadtest nginx/logs/access.log | awk '{print $9, $NF}' | sort | uniq -c | sort -rn
# 10 самых медленных ответов: время, статус, путь
awk '{for (i = NF; i > 0; i--) if ($i ~ /^rt=/) {print substr($i, 4), $9, $7; break}}' \
  nginx/logs/access.log | sort -rn | head
```

## Что подкрутить по итогам

| Наблюдение | Что сделать |
|---|---|
| 503 много, а CPU `wms_front` далеко от 100% одного ядра | поднять `max_conns` в `upstream front` (`nginx/nginx.conf`) |
| CPU `wms_front` 100%, `p(95)` растёт до секунд раньше, чем появляются 503 | опустить `max_conns`: лишним — быстрый 503 (или копия из кэша), остальным — быстрый ответ |
| узкое место — `wms_strapi` или `wms_strapi_db` | это рендер мимо кэша. Посетителям он не грозит, но можно поднять время микрокэша (`proxy_cache_valid` в `location /`) |
| память контейнера упирается в `mem_limit` (`docker-compose.yml`) | поднять лимит; если растёт без плато — утечка |
| исходящий трафик eth0 упирается в одно и то же число | это канал тарифа. Спросить у NetAngels, сколько он и есть ли защита от DDoS |

## Локальная репетиция

Сценарии проверялись на stage с дампом прода (README.md, «Репетиция на своей машине»):
`BASE_URL=https://127.0.0.1 -e INSECURE=1`. Запросы с самой машины приходят в nginx с адреса
docker-сети, а он без лимитов. Чтобы проверить лимиты, нужна отдельная docker-сеть с адресами
вне 172.16.0.0/12 и 192.168.0.0/16. Подключите к ней `wms_nginx`
(`docker network connect`), и тогда запросы с хоста пойдут с её шлюза. Числа с ноутбука в
прод не переносятся: на нём ядра быстрее и их больше.
